================================================================================
BPMN-DSL v2 — Especificação e Lógica de Design
================================================================================

Projeto: Semantic Compression TCC
Autor:   Rafael Marins Florenzano
Data:    2026-05-17
Status:  Design proposal — pendente aprovação antes da implementação

Esta especificação substitui a BPMN-DSL v1 atual (src/dsl/grammar.lark) após
constatadas três limitações funcionais (bugs A/B/C documentados em
src/data/manipulation/deterministic/json_to_dsl.py) e duas limitações
estruturais (refs frágeis por nome; lanes duplicam o fluxo). O objetivo é
oferecer uma representação de processo BPMN 2.0 que seja:

  1. semanticamente completa (todo elemento do JSON-fonte representável sem
     truques como `task "empty"` ou perda de nomes em events);
  2. robusta (refs estáveis, sem dependência de unicidade de nomes);
  3. compressa (objetivo: manter razão de compressão ≥ 85% vs XML BPMN
     canônico — v1 atinge ~91%, aceitamos pequena perda em troca de
     completude semântica);
  4. fácil para o LLM emitir (sintaxe regular, poucas exceções).


================================================================================
1. PRINCÍPIOS DE DESIGN
================================================================================

P1. UM elemento, UMA forma. Cada conceito BPMN tem exatamente uma
    representação sintática. Não há dois jeitos diferentes de declarar a
    mesma coisa.

P2. Nomes são opcionais e SEMPRE posicionais.
    Quando um elemento aceita nome, o nome aparece imediatamente após o
    keyword, antes de quaisquer modificadores. Padrão consistente:
        keyword "Nome opcional" [modificadores...]

P3. IDs separados de nomes.
    Nomes servem para legibilidade; refs (back-edges, loops, comparações)
    usam IDs estáveis (sufixo `#id`). Um nome pode mudar sem quebrar o
    grafo; um ID nunca muda. Apenas elementos referenciados precisam de ID.

P4. Lane é escopo, não declaração separada.
    Em v1 cada task aparece duas vezes (na declaração `lane { ... }` e
    novamente no fluxo). Em v2 o fluxo é declarado uma vez, dentro de
    blocos `@lane "Nome" { ... }` que escopam o pertencimento.

P5. Branches vazias são explícitas.
    O grafo BPMN admite legitimamente uma branch que vá direto ao ponto de
    convergência ("skip"). Representado por `()` — sintaxe inequívoca, sem
    necessidade de tarefa-placebo ou ref-hack.

P6. Composição plana no topo.
    Múltiplos processos, pools, collaborations e annotations podem
    coexistir no nível superior do arquivo. Sem nesting forçado.

P7. Padronização de propriedades.
    Qualquer elemento nomeável aceita `(chave="valor", ...)` para metadados
    (documentation, performer, dueDate, etc.). Sintaxe única, em vez de
    casos especiais por tipo.


================================================================================
2. MUDANÇAS DESTACADAS (v1 → v2)
================================================================================

(a) Events nomeados
    v1: `start`                              (sem nome — bug C)
    v1: `end:error("timeout")`               (nome só via event_kind)
    v2: `start "Início"`                     (nome posicional, opcional)
    v2: `end:error "Timeout do processo"`    (nome posicional, opcional, com kind)

(b) Branches vazias
    v1: `task "empty"` ou `#"<nome do join>"` (workarounds)
    v2: `()` (sintaxe dedicada)

(c) Tasks como ponto de convergência
    v1: corrigido no transpiler (json_to_dsl_v3), mas DSL não impedia o bug
    v2: pode ser explicitamente referenciado por ID (`#proc_order`) em
        múltiplos branches sem ambiguidade

(d) Refs estáveis
    v1: `#"Nome do nó"` (frágil — quebra com rename, colisão de nomes)
    v2: `#order_proc` (CNAME, ASCII, estável). Nomes não são refs.

(e) Lanes
    v1: declaração `lane "X" { task "A", task "B" }` + repetição no fluxo
    v2: escopo `@lane "X" { start -> task "A" -> task "B" }` — declaração única

(f) Multi-processo / collaboration
    v1: já permitia múltiplos top-level, mas semântica de message flow
        entre pools era implícita ("inferida por matching de nomes")
    v2: collaboration pode declarar explicitamente `message ... -> ...`
        cross-pool por ID. Compatível com inferência por nome como fallback.

(g) Subprocess com fluxo interno completo
    v1: `subprocess "X" { seq }` (apenas sequência interna)
    v2: idem, mas o seq interno é um process_body completo (suporta lanes
        internas, gateways, refs, etc.)

3. GRAMÁTICA FORMAL (EBNF — Lark)
================================================================================

// Top-level: zero ou mais constructos paralelos
start: top_level*

?top_level: process
          | pool
          | collaboration
          | note          // annotation autônoma

// ── Process / Pool / Collaboration ────────────────────────────────────────

process:        "process" name id_opt "{" process_body "}"
pool:           "pool"    name id_opt "{" process_body "}"
collaboration:  "collaboration" name id_opt "{" pool+ message_flow* "}"

// Pool e process têm corpo idêntico. Diferença é semântica (pool = ator
// em collaboration; process standalone = single-pool).

?process_body: laneset
             | flow

// Laneset = uma ou mais lanes; flow inferido pela concatenação dos blocos
// (a saída do último elemento de uma lane conecta à entrada do primeiro
// elemento da próxima, se houver "->" no início).
laneset: lane_block+

lane_block: "@lane" name id_opt "{" flow "}"

// Flow = sequência de steps conectados por "->"
flow: step ("->" step)*

?step: event
     | task
     | gateway
     | subprocess
     | call_activity
     | ref
     | empty_branch        // só legal dentro de gateway branch

// ── Events ────────────────────────────────────────────────────────────────

?event: start_event | end_event | catch_event | throw_event

start_event: "start" name? event_spec? id_opt props?
end_event:   "end"   name? event_spec? id_opt props?
catch_event: "catch" name? event_spec  id_opt props?
throw_event: "throw" name? event_spec  id_opt props?

// event_spec encoda trigger (message/timer/error/signal/escalation) e
// payload. Catch e throw exigem event_spec; start e end são opcionais.
event_spec: ":" EVENT_KIND ("(" ESCAPED_STRING ")")?

EVENT_KIND.2: "none" | "message" | "timer" | "error" | "signal" | "escalation"

// Exemplos:
//   start                                        plain
//   start "Recebimento de pedido"                plain com nome
//   start:message "Pedido recebido" #order_in    message com nome e ID
//   end:error "Timeout" (severity="high")        error com nome e props
//   catch:none "Aguardar conclusão"              catch genérico sem trigger
//   catch:timer "PT2H"                           timer (payload=duração ISO)

// ── Tasks ─────────────────────────────────────────────────────────────────

task: TASK_TYPE name id_opt props?

TASK_TYPE.2: "task" | "user" | "service" | "manual" | "script"
           | "send" | "receive" | "rule"

// Nome de task é OBRIGATÓRIO (BPMN exige; sem nome o elemento é inútil).
// Exemplos:
//   user "Aprovar pedido"
//   service "Calcular ICMS" (sla="500ms", retries="3")
//   send "Notificar cliente" #notify_cust

// ── Gateways ──────────────────────────────────────────────────────────────

?gateway: xor_gw | and_gw | or_gw | event_gw

xor_gw:   "xor"   name? id_opt "{" xor_branches "}"
and_gw:   "and"   name? id_opt "{" and_branches "}"
or_gw:    "or"    name? id_opt "{" xor_branches "}"
event_gw: "event" name? id_opt "{" event_branches "}"

xor_branches: cond_branch+
cond_branch:  "[" CONDITION_TEXT "]" "->" branch_target

and_branches: flow (";" flow)*
event_branches: event_branch+
event_branch: "[" event_spec "]" "->" branch_target

?branch_target: flow | empty_branch

empty_branch: "(" ")"

// "default" e "else" são valores válidos de CONDITION_TEXT (transpiler
// marca isDefault=true). CONDITION_TEXT aceita qualquer char exceto [ e ].

// AND usa ';' entre branches (são paralelas, não condicionais).
// XOR/OR/event usam '\n' implícito (uma branch por linha).

// Exemplos:
//   xor "Aprovado?" {
//     ["sim"]     -> service "Registrar"
//     ["não"]     -> end "Rejeitado"
//     [default]   -> end "Pendente"
//   }
//
//   xor {
//     ["pular"]   -> ()                        // empty branch explícita
//     ["fazer"]   -> task "Processar"
//   }
//
//   and "Notificar canais" {
//     send "Email"   -> task "Log email";
//     send "SMS"     -> task "Log SMS"
//   }
//
//   event "Aguardar evento" {
//     [:message "approval"]   -> task "Aprovar"
//     [:timer "PT30M"]        -> end:error "Timeout"
//   }

// ── Subprocess / Call activity ────────────────────────────────────────────

subprocess:    "subprocess" name id_opt "{" process_body "}"
call_activity: "call" name id_opt props?      // referencia processo externo

// ── Referência / loop ─────────────────────────────────────────────────────
// Ref aponta para um elemento previamente declarado (por ID). Usada para:
//   - back-edges (loops)
//   - convergência explícita (vários branches apontando ao mesmo nó)

ref: "#" CNAME

// Exemplos:
//   user "Submeter" #submit
//   ...
//   xor {
//     ["retry"] -> #submit                    // back-edge para Submeter
//     ["done"]  -> end "OK"
//   }

// ── Annotation ────────────────────────────────────────────────────────────
// Não participa do fluxo; preserva texto livre para auditoria/observação.

note: "note" ESCAPED_STRING id_opt

// ── Message flow (apenas dentro de collaboration) ─────────────────────────
// Modelo explícito de comunicação entre pools.

message_flow: "message" name? "from" ref "to" ref props?

// Exemplo (dentro de collaboration):
//   message "Pedido" from #order_send to #order_recv

// ── ID opcional ───────────────────────────────────────────────────────────

id_opt: ( "#" CNAME )?

// ── Propriedades ──────────────────────────────────────────────────────────

props: "(" prop ("," prop)* ")"
prop:  CNAME "=" ESCAPED_STRING

// Chaves reservadas (semântica BPMN específica):
//   - lane         : sobrescreve escopo @lane atual (uso raro; preferir
//                    estrutura @lane { ... })
//   - performer    : recurso/papel responsável (BPMN performer)
//   - documentation: texto livre BPMN documentation
//   - dueDate      : ISO-8601 timestamp / duration
//   - assignee     : usuário atribuído (para userTask)

// ── Terminais auxiliares ──────────────────────────────────────────────────

name:            ESCAPED_STRING
CONDITION_TEXT:  /[^\[\]]+/

%import common.ESCAPED_STRING
%import common.CNAME
%import common.WS
%ignore WS
%ignore /\/\/.*/

5. REGRAS DE FLUXO E TRANSPILAÇÃO
================================================================================

R1. Concatenação implícita.
    A operadora `->` cria sequenceFlow entre o lado esquerdo (origem) e o
    lado direito (alvo). Em `A -> B -> C`, dois sequenceFlows são gerados:
    A→B e B→C.

R2. Gateway split implícito, merge implícito.
    `xor "Q?" { [a] -> A   [b] -> B }` gera:
        sequenceFlow entrada → exclusiveGateway(Q?)
        sequenceFlow exclusiveGateway → A (cond=a)
        sequenceFlow exclusiveGateway → B (cond=b)
    O ponto de convergência é determinado por o que vem APÓS o bloco:
        `xor { ... } -> next` insere um exclusiveGateway de merge antes
        de `next`.
    Se não houver `-> next` após o gateway, as branches terminam
    independentemente (sem merge).

R3. AND split + AND join automáticos.
    `and { A; B }` gera <parallelGateway> de split, dois fluxos, e
    <parallelGateway> de join se houver continuação `-> next`. Sem
    continuação, branches terminam paralelamente.

R4. Empty branch `()`.
    Sintaticamente: legível somente como conteúdo de uma branch de gateway
    XOR/OR. Semanticamente: gera sequenceFlow direto do gateway para o
    próximo ponto de convergência (o merge gateway que vier após).
    Equivale ao padrão BPMN de "skip path".

R5. Resolução de refs.
    `#id` resolve para o elemento previamente declarado com `#id` no
    mesmo process/pool. Se não encontrado:
      - dentro de collaboration: busca em todos os pools antes de falhar
      - fora: erro de transpilação
    Refs criam sequenceFlows de back-edge sem inserir novo nó.

R6. Lane escopo + element override.
    Dentro de `@lane "X" { ... }`, todo elemento herda lane=X.
    Sobrescrita pontual: `task "Y" (lane="Z")` — útil quando uma única
    atividade pertence a outra lane sem quebrar o bloco.

R7. Múltiplos processes no mesmo arquivo.
    Cada `process`/`pool` é independente — refs não cruzam fronteira de
    process (use `collaboration` + `message ... from ... to ...` para
    relações cross-pool).

R8. Tasks como ponto de convergência.
    Quando uma task é alcançada por múltiplos caminhos (in-degree ≥ 2),
    a forma idiomática é dar ID à task e referenciá-la dos branches que
    não a contêm naturalmente no fluxo principal. Exemplo:
        user "Processar" #proc
        ...
        xor {
          ["caminho A"] -> task "X" -> #proc
          ["caminho B"] -> #proc                  // direto ao convergência
        }

R9. Validação obrigatória pelo transpiler.
    Antes de emitir XML, o transpiler verifica:
      - exatamente 1 startEvent por process (não applicável a sub-flows)
      - ≥ 1 endEvent por process
      - todos os refs resolvem
      - IDs são únicos dentro do mesmo escopo
      - lanes referenciadas existem
      - XOR/OR branches têm condição (ou marcam default)
      - AND branches NÃO têm condições


================================================================================
6. ECONOMIA DE TOKENS
================================================================================

Comparação para o processo "Aprovação de Férias" (exemplo do prompt
BPMN_JSON_generator.md, ~9 nodes, ~9 flows, 3 lanes):

  - XML BPMN canônico (com BPMNDiagram):  ~3.500 chars / ~1.200 tokens
  - JSON intermediário:                    ~1.400 chars /   ~500 tokens
  - DSL v1 (atual):                          ~520 chars /   ~190 tokens
  - DSL v2 (proposto):                       ~480 chars /   ~175 tokens

Estimativas — necessário medir empiricamente após implementação. v2 é
ligeiramente mais conciso porque:
  - elimina duplicação lane+flow (-15 a -30% em processos com lanes)
  - empty branches `()` em vez de `task "empty"` (-3 chars por ocorrência)
  - refs por CNAME `#proc` em vez de `#"Nome longo do nó"` (-10 a -20
    chars por ref)

E ligeiramente mais verboso em casos sem lanes (escopo `@lane` é overhead
em processos single-lane — mas a maioria tem ≥ 2 lanes).

Razão de compressão alvo vs XML: ≥ 85%. Razão atual v1: ~91%. Aceitação
da pequena perda em troca de completude semântica e robustez de refs é
explicitamente parte do trade-off de design.

7. EXEMPLOS COMPLETOS
================================================================================

EXEMPLO 1 — Aprovação simples (1 fork XOR, 3 lanes, 2 ends):
─────────────────────────────────────────────────────────────────────────

process "Aprovação de Férias" {
  @lane "Funcionário" {
    start "Início"
    -> user "Solicitar férias no sistema" #req
  }
  @lane "Gestor" {
    -> receive "Receber notificação"
    -> user "Analisar solicitação"
    -> xor "Aprovada?" #decide {
      ["sim"] -> service "Registrar no sistema" -> send "Notificar aprovação" -> end "Fim aprovado"
      ["não"] -> send "Notificar recusa" -> end "Fim recusado"
    }
  }
  @lane "RH" {
    note "Registro e notificação são executados pelo RH automaticamente"
  }
}

(Note: a lane RH neste exemplo não tem elementos diretos — apenas uma
annotation. Forma válida.)


EXEMPLO 2 — Loop com back-edge (retry pattern):
─────────────────────────────────────────────────────────────────────────

process "Processamento com Retry" {
  start
  -> service "Buscar dados" #fetch
  -> service "Validar"
  -> xor "Válido?" {
    ["sim"]     -> service "Processar" -> end
    ["não"]     -> xor "Tentar novamente?" {
                     ["sim"] -> #fetch                  // back-edge
                     ["não"] -> end:error "Inválido"
                   }
  }
}


EXEMPLO 3 — Paralelismo (AND) com merge explícito:
─────────────────────────────────────────────────────────────────────────

process "Notificação Multi-canal" {
  start
  -> task "Preparar mensagem"
  -> and "Disparar notificações" {
       send "Enviar e-mail"   -> service "Registrar log e-mail";
       send "Enviar SMS"      -> service "Registrar log SMS";
       send "Enviar push"     -> service "Registrar log push"
     }
  -> user "Confirmar entregas"
  -> end "Fim"
}


EXEMPLO 4 — Collaboration com message flow:
─────────────────────────────────────────────────────────────────────────

collaboration "Pedido entre Cliente e Vendedor" {
  pool "Cliente" {
    start
    -> user "Selecionar produto"
    -> send "Enviar pedido" #cli_send
    -> receive "Aguardar confirmação" #cli_recv
    -> end
  }
  pool "Vendedor" {
    start:message "Receber pedido" #ven_recv
    -> service "Validar estoque"
    -> xor "Disponível?" {
      ["sim"] -> send "Confirmar pedido" #ven_send -> end
      ["não"] -> send "Rejeitar pedido" #ven_reject -> end:error "Sem estoque"
    }
  }
  message "Pedido" from #cli_send to #ven_recv
  message "Confirmação" from #ven_send to #cli_recv
  message "Rejeição" from #ven_reject to #cli_recv
}


EXEMPLO 5 — Skip branch (uso de `()`):
─────────────────────────────────────────────────────────────────────────

process "Cadastro com Endereço Opcional" {
  start
  -> user "Preencher dados pessoais"
  -> xor "Informou endereço?" {
    ["sim"] -> user "Validar CEP" -> service "Geocodificar"
    ["não"] -> ()                                        // skip explícito
  }
  -> service "Persistir cadastro"
  -> end
}

================================================================================
9. FORA DE ESCOPO (deferido / não suportado)
================================================================================

NS1. Conditional sequence flows fora de gateways.
     BPMN permite que sequenceFlows comuns tenham conditionExpression.
     A DSL v2 só representa condições dentro de XOR/OR/event branches.
     Justificativa: padrão raro; emular via XOR sem perda semântica.

NS2. Compensation handlers, boundary events, transactions.
     Conceitos BPMN avançados não cobertos pela primeira versão. Acomodação
     futura via nova keyword `boundary` ou `compensate` quando necessário.

NS3. Data objects, data inputs/outputs explícitos.
     BPMN permite modelar dados como first-class. v2 considera dados
     implícitos no nome da task (`service "Calcular total a partir do
     pedido"`). Para representação explícita, usar props
     `(input="...", output="...")`.

NS4. Multi-instance markers.
     Padrões tipo "execute para cada item da lista". Acomodação futura.

NS5. Gateways complexos (complex gateway).
     Raros e mal-padronizados. Mapear para XOR/OR pelo transpiler.

NS6. BPMN diagram (BPMNDI — layout visual).
     Gerado deterministicamente pelo transpiler dsl_to_xml via layout
     hierárquico (Sugiyama simplificado, conforme CLAUDE.md). DSL não
     representa coordenadas.


================================================================================
10. CHECKLIST DE COMPLETUDE SEMÂNTICA (validação contra JSON intermediário)
================================================================================

Para cada amostra processada, garantir:

[ ] Todos os nodes do JSON aparecem no DSL (no fluxo OU em lane scope).
[ ] Quantidade de events match: count(startEvent JSON) == count(start na DSL)
    (idem para endEvent, intermediates).
[ ] Quantidade de tasks match: count por tipo no JSON == count por keyword no DSL.
[ ] Quantidade de gateways match.
[ ] Lanes: nomes idênticos (set-equal). Cardinalidade de membros pode
    diferir em caso de override pontual via props (lane="X").
[ ] Toda flow do JSON tem correspondente no DSL (via -> direto ou via ref).
[ ] Condições de XOR/OR branches preservadas literalmente.
[ ] Nomes de events e tasks preservados literalmente.
[ ] Refs no DSL resolvem para IDs declarados; nenhuma ref órfã.
[ ] Pool/process names preservados.
[ ] Properties (documentation, performer, etc.) preservadas.

11. NOTAS DE IMPLEMENTAÇÃO (para o transpiler json_to_dsl_v6)
================================================================================

I1. Geração de IDs.
    Estratégia: usar os IDs do JSON-fonte diretamente como ID DSL quando
    o ID for um CNAME válido (alfanumérico + underscore). Quando não for
    (ex: contém hífen, espaço), gerar ID derivado por slugificação:
        "T-01"  → t_01
        "Order Process" → order_process
    Apenas atribuir ID a elementos que serão referenciados (in-degree ≥ 2
    OU alvo de back-edge). Quando o alvo é um gateway de join/roteamento que
    não será emitido como elemento explícito na DSL, o ID é transferido para
    o próximo nó emitido no fluxo. Isso evita refs órfãs como `#g05` para um
    merge que foi compactado pela estrutura do bloco.

I2. Ordem dos blocos @lane.
    Ordenar lanes por primeira aparição no fluxo principal (BFS desde
    startEvent). Determinístico e estável entre execuções.

I3. Quebra de fluxo entre lanes.
    Quando o fluxo "sai" de uma lane e entra em outra, o transpiler
    fecha o bloco `@lane "X" { ... }` e abre `@lane "Y" { -> ... }`.
    O `->` inicial sinaliza continuidade (sequenceFlow de saída do
    último elemento da lane anterior para o primeiro da nova).

I4. Detecção de message flow em collaboration.
    Quando o JSON tem múltiplos pools (caso `processos: [...]` da seção
    de unwrap atual), o transpiler:
      - emite `collaboration "..." { pool ... pool ... }`
      - detecta sendTask + receiveTask com nomes correspondentes e emite
        `message "..." from #send_id to #recv_id`
      - fallback: nenhum message inferido se nomes não casarem

I5. Empty branches.
    Gerar `()` quando uma branch de XOR/OR linearize para zero steps
    com end_boundary definido. Substitui o atual `task "empty"`.

I6. Cycles.
    Detectar back-edges via DFS antes do linearize. Para cada nó alvo
    de back-edge, garantir que ele tenha ID e emitir `#<id>` no(s)
    branch(es) de origem. Elimina a heurística de cycle ref por nome
    do v3.

I7. Validação pré-emissão.
    Antes de devolver a string DSL, executar checklist da seção 10 e
    levantar exception com mensagem detalhada em caso de violação.
    Impede que DSL semanticamente incompleta passe silenciosamente.

12. TRANSPILAÇÃO DSL → BPMN XML (dsl_to_xml)
================================================================================

Objetivo.
    A etapa `dsl_to_xml` materializa a DSL compacta em XML BPMN 2.0 explícito.
    A DSL é intencionalmente econômica; o XML, por outro lado, exige IDs,
    sequenceFlows, gateways, laneSets e referências concretas. Portanto, esta
    etapa não deve reinterpretar o processo: ela deve expandir as convenções
    da DSL sem inventar fluxo novo.

Arquitetura.
    O motor de conversão fica em `src/transpiler/xml.py`.
    O script `src/data/manipulation/deterministic/dsl_to_xml.py` é apenas o
    runner batch:

      dsl_transpiler_runs.output_dsl
          → src.transpiler.transpile()
          → validação XML mínima
          → xml_transpiler_runs

    A tabela `xml_transpiler_runs` armazena cada tentativa com:
      - sample_id e source_dsl_run_id;
      - versão de origem (`source_dsl_version`) e versão XML
        (`xml_transpiler_version`);
      - input_dsl e output_xml;
      - status, xml_ok, warnings e erro/traceback quando houver falha.

Estados do runner.
      succeeded          XML gerado, bem-formado, IDs únicos.
      transpile_failed   parser/transpiler levantou exceção.
      xml_failed         XML foi gerado, mas falhou validação mínima.
      transpile_timeout  orçamento por amostra excedido.

Validação atual.
    Como o repositório ainda não contém os XSDs BPMN, a validação inicial é:
      1. XML bem-formado via lxml;
      2. unicidade global de atributos `id`.

    A validação XSD deve ser adicionada depois que os schemas BPMN 2.0 forem
    versionados no repositório. Até lá, `xml_ok=1` significa “XML estruturalmente
    formado para auditoria”, não conformidade XSD completa.

Regras de expansão.

T1. Operador `->`.
    Cada conexão A -> B vira `<sequenceFlow sourceRef=A targetRef=B>`.
    Quando A ou B é um bloco de gateway, o source/target efetivo é o gateway
    split/join criado pelo transpiler.

T2. Gateway split/merge implícito.
    `xor`, `or`, `and` e `event` criam um gateway de entrada (split) e um
    gateway de saída (merge) quando o bloco continua com `-> próximo`.
    Branches que terminam em `()` geram fluxo direto do split para o merge.

T3. Refs.
    `#id` deve resolver preferencialmente para um elemento que declarou `#id`.
    O ref não cria nó novo; ele cria sequenceFlow para o nó existente.
    Refs não resolvidos são erro do transpiler XML, pois indicam DSL
    semanticamente incompleta.

    Compatibilidade: para DSLs já persistidos antes da correção de IDs, o
    transpiler XML também aceita fallback por slug do nome de um nó já emitido
    no mesmo processo. Exemplo: `user "Acessar página"` pode ser referenciado
    por `#acessar_p_gina`. Esse fallback não substitui a regra principal; o
    json_to_dsl deve continuar emitindo IDs explícitos quando sabe que um nó
    será alvo de ref.

T4. Lanes.
    `@lane "X" { ... }` é escopo de pertencimento. No XML, isso vira:
      - `<laneSet>`;
      - uma `<lane name="X">`;
      - `<flowNodeRef>` para cada nó emitido naquele escopo.

    Overrides `(lane="Y")` dentro de uma branch representam exceção pontual
    de lane no DSL. O transpiler XML deve materializar esse pertencimento sem
    duplicar o nó.

T5. Eventos intermediários genéricos.
    `catch:none "Aguardar"` vira `<intermediateCatchEvent name="Aguardar">`
    sem `eventDefinition`. Isso preserva `intermediateCatchEvent` do JSON
    quando a LLM não informou se o evento era timer/message/signal.

T6. Múltiplos top-level processes.
    A gramática aceita vários `process` no mesmo arquivo DSL. O XML também
    pode conter vários `<process>`, mas todos os `id` precisam ser únicos no
    documento inteiro. Por isso o `src/transpiler/xml.py` usa um contexto
    global de alocação de IDs para `process`, `laneSet`, `lane`, gateways,
    eventos, tarefas e sequenceFlows. O runner ainda valida duplicidade para
    capturar regressões.

T7. Collaboration.
    `collaboration { pool ... message ... }` vira:
      - `<collaboration>`;
      - `<participant processRef=...>` por pool;
      - `<messageFlow sourceRef=... targetRef=...>` para cada message.

Pontos de atenção conhecidos.
    - O transpiler XML atual ainda emite XML sem BPMNDI/layout visual.
      Isso é suficiente para validação estrutural, mas não para abrir em
      modeladores que exigem diagrama.
    - Refs forward continuam frágeis porque a emissão XML é single-pass por
      processo. O uso esperado de `#id` é para loops ou reconvergências em
      nós já emitidos. Caso surjam muitos refs forward legítimos, o XML
      transpiler deve ganhar uma etapa de pré-registro de IDs.
    - Gateways de merge puro podem não aparecer como nó nomeado no DSL; isso
      é esperado, pois o merge é representado pela continuação após o bloco.

Correções observadas na rodada json_to_dsl_v5 / dsl_to_xml_v1.
    A primeira execução em lote do XML teve 904 sucessos em 1047 amostras.
    A análise dos 143 `ValueError` mostrou dois padrões dominantes:

      1. IDs XML duplicados em documentos com múltiplos `process`, porque os
         contadores eram reiniciados por processo.
      2. Refs DSL apontando para gateways de roteamento (`#g05`, `#p02`, etc.)
         que o próprio json_to_dsl simplificava e não emitia como nó explícito.

    A correção foi dividida em duas partes e versionada como
    `json_to_dsl_v6` + `dsl_to_xml_v2`:

      - `dsl_to_xml`: introduzir `XmlContext` global para IDs de documento e
        fallback por slug de nome para DSLs antigos já persistidos.
      - `json_to_dsl`: redirecionar refs de gateways join/degenerados para o
        próximo nó realmente emitido no fluxo, garantindo que esse nó receba
        ID explícito.

    Resultado de validação local:
      - usando os DSLs v5 já persistidos: 1039/1047 passaram no novo XML;
      - regenerando o DSL a partir do JSON com o código corrigido: 1047/1047
        passaram na transpilação DSL -> XML.
